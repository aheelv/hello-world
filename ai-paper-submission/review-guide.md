## 摘要

大语言模型驱动的智能体正从"单体能力演示"转向"系统级生产部署"，瓶颈随之由模型推理能力迁移到组合、交付、验证与治理等系统性问题。与此同时，"Harness"一词在文献与产业中呈现出三层含义：作为软件交付平台的 Harness、作为智能体运行时脚手架的 agent harness，以及作为一般性集成基础设施的智能体集成平台。本文对这三层含义作出界定，并提出一个七层参考架构；进而梳理系统工程（Systems Engineering, SE）理论与方法在智能体设计、部署、运维中的映射路径，包括 ISO/IEC/IEEE 15288 生命周期过程、需求与架构描述、接口契约、验证与确认（V&V）、配置与状态治理、可靠性工程及 AI 治理标准。在此基础上，归纳智能体编排、CI/CD 自动化、可观测性与治理四条交叉研究主线，对比八类代表性平台/框架在十一个维度上的能力分布，指出当前工业实践多处于"流程级融合"、学术研究多处于"理论级倡议"，二者之间缺乏可检验的桥接方法这一核心缺口。最后评估该方向的论文投稿潜力，给出六个可操作选题、目标期刊/会议清单、研究设计与写作模板及常见拒稿风险。本文认为：单纯的描述性综述已难以进入 SCI 一区/CCF A 类期刊，但以系统化文献综述（SLR）为证据基础、以"接口契约—运行时状态治理"为理论切口、并辅以可复现实证或工业多案例研究的工作，具备明确的 SCI Q1 / CCF A 类投稿潜力。经万方中文文献补检（第 6 章），"产业在 L2、学术在 L3"的断层判断收窄为"已有中文桥接雏形但缺少真实平台上的受控验证"，并补充了中国智能体专项政策与中文同行评议实证，标准缺位的表述相应调整。

**关键词**：智能体集成平台；Harness；系统工程；智能体编排；CI/CD；可观测性；AI 治理；系统智能

## 1 引言

### 1.1 问题背景

2023 年以来，基于大语言模型（LLM）的智能体研究经历了从"统一架构框架"[10] 到"多智能体协同"再到"系统智能"的范式演进。Feng 等人把这一演进链概括为：模型智能（预训练/后训练）→ 模型能力激发（提示工程、上下文工程）→ 个体智能（**Harness Engineering** 与 Loop Engineering，即 Agent = Loop(LLM + Harness)）→ **系统智能**（Graph Engineering，用显式图结构组织任务、智能体与运行时状态）[6]。这一划分的关键判断是：个体智能体存在结构性上限——单循环被迫将可并行的子任务串行化、把异质专业判断挤入同一上下文、错误沿轨迹传播而难以定位；单纯增加智能体数量并不解决问题，因为"智能必须在系统层面被组织"[6]。

产业侧给出了同一问题的另一个证据。Harness 在 2025 年融资公告中援引其客户数据指出，工程团队仅有 30%—40% 的时间用于编写与迭代代码，其余 60%—70% 消耗在测试、部署、安全、合规与优化的"外环（outer loop）"；AI 生成代码量以约 4 倍速度增长，进一步放大了"写得快、交得慢"的剪刀差[1]。换言之，智能体规模化之后，约束条件不再是模型能力，而是**交付系统的吞吐、可靠性与可审计性**——这恰是系统工程自 20 世纪中叶以来处理的核心问题。

学术界对此已有明确回应。IBM Research 的立场论文《Agentic AI Needs a Systems Theory》主张：当前 AI 开发过度聚焦单一模型能力，忽视由智能体—环境—智能体交互产生的涌现行为，因而系统性低估了能力上限与风险；该文把智能体系统形式化为由人类团队、智能体集合、环境、工具集、策略集、结果模型集与适应机制构成的多元组，并强调"功能性能动性（functional agency）"是在系统层面涌现、而非存在于任何单个智能体内部的属性[5]。Beheshti 等人进一步指出，智能体生态正在"临时地（ad hoc）"重造服务计算社区研究了二十余年的组合、互操作、QoS、生命周期管理、治理与信任问题，并提出 Agentic Service-Oriented Computing（ASOC）六项基础原则：harness-ability、composability、lifecycle engineering、trustworthiness by design、goal-driven orchestration、observability/accountability[7]。

中文学界给出了同向且更直接的判断。《软件学报》2026 年综述把代码生成智能体的第三大特征概括为"工程实践性的增强"——研究重心从模型算法创新转向流程管理、系统可靠性与工具集成[W-1]；CCF 会刊《计算》则明确指出 LLM 在复杂软件生成中受限于规模化、可信性与稳定性三重挑战，"并非银弹"，须与传统软件工程方法深度融合[W-15]。这与"瓶颈已迁移到系统性工程问题"的判断一致，且把证据基础从厂商数据扩展到中文同行评议文献（详见 6.1）。

### 1.2 概念界定

"Harness"在当前语境下有三种互不替代的用法，若不先行区分，极易造成综述对象错位：

| 层面 | 指称 | 代表 | 本文用法 |
|---|---|---|---|
| (a) 专有平台 | Harness Inc. 的 AI 软件交付平台 | Harness AI / Software Delivery Knowledge Graph / Delegate[1][2] | "Harness 平台" |
| (b) 技术术语 | 智能体运行时脚手架，包裹模型、工具、状态与控制回路 | SWE-agent 的 Agent-Computer Interface (ACI)[11]、OpenHands 的事件流架构[12]、LangChain `create_agent` 的 "highly configurable harness"[27] | "agent harness / 运行时框架" |
| (c) 一般类别 | 把模型、工具、数据、策略、执行、观测与交付集成为可治理系统的基础设施 | LangGraph、Microsoft Agent Framework、Google ADK、Bedrock AgentCore、Dify 等 | "智能体集成平台" |

值得强调的是，(a) 与 (b) 在词源上同源：二者都指"为智能能力套上可控制、可观测、可复现的外部结构"。SWE-agent 的核心发现即是：暴露给模型的编辑工具与 shell 工具本身就是**可设计的接口**——把编辑窗口收窄、每次编辑后返回 linter 输出、加入显式 submit 动作，能在同一模型上显著改变任务成功率[11]。这一"接口决定系统行为"的结论，与系统工程中的接口管理、与 Harness 平台"每个动作都在策略边界内执行"的设计[2] 是同构的。本文因此在 (c) 的意义上使用"智能体集成平台"，并以 Harness 平台作为产业侧的代表性案例解剖对象。

## 2 分类梳理

### 2.1 主流智能体集成平台架构与核心能力

#### 2.1.1 七层参考架构

综合 ASOC 六原则[7]、图工程三张图[6]、Agent Platform Engineering 的七层划分及 Harness 的三层结构[1][2]，可归纳出一个与具体产品无关的参考架构：

1. **上下文与知识层**：代码、服务、部署、测试、事件、策略、成本信号的统一语义模型；代表为 Harness Software Delivery Knowledge Graph[1][2]、RAG/向量库、企业本体。
2. **推理与编排层**：任务分解、规划、路由、专家智能体与工作者智能体的分工、人在回路节点；图引擎或状态机实现确定性控制[6][27]。
3. **工具与互操作层**：工具注册、schema 管理、权限分级；MCP 负责"智能体—工具/数据"，A2A 负责"智能体—智能体"[24][25]。
4. **运行时与隔离层**：沙箱/容器、Delegate 或 VPC 内执行、密钥本地化、身份与工作负载凭证、幂等与重试[2][12]。
5. **状态与记忆层**：短期工作记忆、情节记忆、检查点与可恢复执行、共享状态的并发控制[6][27]。
6. **治理与策略层**：策略即代码（OPA/Rego）、RBAC、审批门、变更窗口、自治度分档、签名审计与证据链[2][16]。
7. **可观测性、评估与交付层**：全链路 trace、评估门禁、DORA 类交付指标、持续验证与自动回滚[3][4][16][26]。

这七层并非堆叠，而是两条贯穿线：**控制面**（需求→契约→策略→证据）与**数据面**（上下文→推理→工具→状态→遥测）。系统工程的价值主要体现在控制面，而当前多数开发框架的能力集中在数据面——这正是后文 3.2 节要讨论的结构性失衡。

#### 2.1.2 平台形态分类

按"主要交付物"可分为四类（企业视角的概念化工作亦已出现：Li 等区分了单体智能体与协作式智能体系统，归纳现代智能体系统的六项核心能力，并提出覆盖设计、治理、人机协作与平台生态的研究议程[15]）：

- **开发框架型**：LangGraph（图/状态机、检查点、中断恢复、LangSmith 追踪）[27][R-1]、Microsoft Agent Framework（合并 AutoGen 与 Semantic Kernel，会话式多智能体 + 企业身份）[R-1]、CrewAI（角色/任务驱动，快速原型）、Google ADK（结构化多智能体工程）、Dify / Coze（低代码可视化）。优势是表达力与社区，弱项是治理与交付闭环多为外挂。
- **云托管运行时型**：Azure AI Foundry Agent Service（Entra Agent ID、VNet、OpenTelemetry）、AWS Bedrock AgentCore（VPC 隔离、托管运行时）、Vertex AI Agent Engine（评估与部署一体化）[R-1][28][29][30]。优势是身份、网络、审计开箱即用，弱项是与特定云强绑定。
- **软件交付/DevOps 平台型**：以 Harness AI 为代表，把智能体嵌入既有 CI/CD、测试、安全、成本与 GitOps 流水线[1]—[4]；GitHub Copilot coding agent 则把智能体原生嵌入 issue/PR 工作流[R-2]。优势是天然承接变更管理、审批与回滚，弱项是智能体编排的学术表达力有限。
- **研究型 harness**：SWE-agent[11]、mini-SWE-agent、OpenHands[12]、Agentless[14]，围绕 SWE-bench[13] 等基准，把"接口设计"本身作为研究对象，提供可复现的实验台。

> 说明：上标 [R-1][R-2] 指产业与二级资料，见文末 B 组，非同行评议来源。

#### 2.1.3 案例解剖：Harness 平台的架构取向

Harness 自 2025 年起把自身定位为"AI for Everything After Code"的 AI 软件交付平台，其公开架构包含三个基础层[1]：

- **面向交付的专用智能体库**：覆盖交付、测试、验证、安全、治理与运维任务；产品页进一步区分为 **Expert Agents**（推理、调查、解释、建议）与 **Worker Agents**（执行构建、触发测试、管理回滚、扩缩容）[2]。
- **Software Delivery Knowledge Graph**：统一映射代码变更、服务、部署、测试、环境、事件、策略与成本信号，作为所有智能体的共享上下文[1][2]。这一层在方法论上等价于 MBSE 的"单一事实源/数字线程"，是平台区别于普通编排框架的核心。
- **企业级编排引擎**：把 AI 判断转化为跨流水线、跨环境的一致自动化，并保证决策以可预测方式落地[1]。

治理设计尤其值得注意：所有智能体动作在客户 VPC/集群内经 Harness Delegate 执行，密钥不出边界；OPA 策略、RBAC、审批与变更窗口对智能体与人类"同一套身份、同一套策略、同一套执行、同一套证据"；每个动作被归因、记录、签名，输出为可供审计的 scorecard 与审计轨迹；验证失败自动回滚；自治度按任务、环境、团队分档（Autonomous / Human-in-the-loop / Deterministic）[2]。2025 年公布的能力还包括：Autonomous Code Maintenance（意图驱动的依赖升级、陈旧 feature flag 清理、CI 自愈 Autofix、单测补全）、AI Verification and Rollback（自动发现观测指标、构建健康画像、异常回滚）、Architect Mode（对话式生成符合组织标准的流水线）、IDP Knowledge Agent[3]；2025 年 11 月又加入基于知识图谱与 Harness MCP Server（暴露 160+ 工具）的 AI 数据库迁移生成、流水线 Error Analyzer、以及按任务动态选模与护栏回退[4]。

从 SE 视角看，Harness 的实质是**把智能体当作"变更主体"纳入既有配置管理与变更控制体系**，而不是另建一套智能体治理体系。这一取向的优点是合规成本低、可审计性天然具备；代价是智能体自主性的表达受限于流水线模型，对开放环境下的涌现行为缺乏刻画。

### 2.2 系统工程理论与方法在智能体设计、部署、运维中的应用

#### 2.2.1 理论支点：涌现、边界与系统层属性

系统工程的经典命题是"整体大于部分之和"，其工程含义是：系统层属性不可由组件属性线性推出，因此必须为涌现行为单独设立观测与控制机制。Miehling 等人把这一命题引入智能体 AI，指出简单智能体仅凭与环境及其他智能体的交互即可涌现出增强认知、因果推理与元认知意识，故风险评估不能以单模型评测代替[5]。这一论点在实证侧得到呼应：Cemri 等人用扎根理论分析 7 个框架的执行轨迹，提出 MAST 分类法（14 种失效模式，归为规格与系统设计、智能体间错位、任务验证与终止三类），并发现改进角色规格或调整拓扑虽能提升成功率，却无法消除失效，说明需要**结构性重新设计**而非提示修补[9]；不同二手资料对三类占比的报告存在差异（约 41%/37%/21% 与 44%/32%/24%），引用时须回到原始版本核对，不宜作为确定常数。另有立场性工作指出，相当一部分所谓"协调失败"本质是并发控制问题（陈旧读、丢失更新），应引入冲突检测、隔离保证与结构化共享资源访问[6]。

**万方核对新增（6.2）**：张珑耀等的特邀综述[W-2] 以 7 个代表性 MAS、13 418 段运行轨迹、LLM 初筛加专家人工校验，构建了与 MAST 不同的四层异常分类（模型理解感知、智能体交互、任务执行、外部环境），报告智能体交互异常 16.8%、任务执行异常 27.1%、外部环境异常 18.3%，并指出模型理解感知异常为根源性诱因。两套分类法的层级划分与占比口径不同，**不可混用为同一组常数**；MAST 三分类与 [W-2] 四分类应并列呈现。

#### 2.2.2 生命周期过程：ISO/IEC/IEEE 15288 与 ISO/IEC 42001

ISO/IEC/IEEE 15288:2023（第 2 版）建立了覆盖构思、开发、生产、使用、支持与退役的通用生命周期过程框架，明确不规定具体生命周期模型或方法，可递归、迭代、并发地应用于系统及其元素，并适用于体系（system of systems）[17]。这一"不绑定方法"的特性使其可直接映射到智能体系统：

| 15288 过程组 | 智能体系统对应活动 | 现状 |
|---|---|---|
| 协议过程（获取/供应） | 模型与工具供应商选择、SLA 与数据边界、第三方 MCP Server 准入 | 实践零散 |
| 组织级项目使能 | 智能体资产清单、能力基线、复用与技能库、人员角色 | 早期 |
| 技术管理过程 | 智能体项目规划、风险评估、配置管理、决策管理、质量保证 | 部分被 MLOps/LLMOps 覆盖 |
| 技术过程 | 业务需求→智能体需求、架构定义、设计、实现、集成、验证、确认、运行、维护、处置 | 概念映射尚不完整 |

ISO/IEC 42001:2023 是首个可认证的 AI 管理体系标准，以 PDCA 循环组织 AI 方针、风险评估、全生命周期控制、数据治理、绩效评价与持续改进，覆盖设计、开发、测试、部署、运行与退出[18]。它补上了 15288 缺少的"组织级治理"维度（配套风险管理指南见 ISO/IEC 23894:2023[19]）；在智能体场景中，其"AI 系统清单—风险分层—控制措施—审计证据"的结构与 NIST AI RMF 的 GOVERN/MAP/MEASURE/MANAGE 四职能[20]、生成式 AI 画像 NIST AI 600-1[21] 共同构成治理骨架。EU AI Act（Regulation (EU) 2024/1689）第 12 条要求高风险 AI 系统在全生命周期自动记录事件日志、第 15 条要求对对抗性输入具备韧性[22]；OWASP Top 10 for LLM Applications 2025 中 LLM06 "Excessive Agency"（过度代理）则直接指向智能体的权限边界[23]。这些条款把"可观测性"与"最小权限"从工程最佳实践提升为合规义务。

#### 2.2.3 需求、架构与可追溯性：MBSE 与智能体的双向关系

MBSE 工具链的智能化是当前"SE 吸收智能体"最实质的方向。以 GenAI Workbench 与 Intelligent Design 4.0 为代表的工作，把智能体作为**数字线程中的一等参与者**：以基于开源 PLM/CAD 内核的数据主干、文档/几何/图谱的模块化存储、UID 索引的跨模态 API 接入智能体编排层；由无状态微智能体（需求抽取、架构综合）经 Agentic Orchestrator 与事件驱动消息总线协调；在标准化 SysML 产物（需求、模块图、参数图、V&V 报告）之上叠加阶段级与功能级智能体，通过发布/订阅总线与 XMI、FMI 等交换格式运作[R-3]。输入端则用 OCR 与视觉-LLM 处理文档、BERT+CRF 抽取需求、STEP/B-Rep 解析几何、XMI 转图谱，最终以 UID 索引统一[R-3]。

**万方核对补充（6.3）**：原稿此处主要依赖二级资料 [R-3]，现可用中文一手文献替换与补强。毛寅轩等[W-3] 系统论述 LLM 使 AI 从"点状分析工具"转变为"贯穿生命周期的生成式智能协作助手"，覆盖需求分析、系统设计、验证确认、知识管理四环节；鲁金直等[W-4] 提出 KARMA 多架构统一建模语言与 LLM、计算机视觉、三维建模融合的"空间智能"MBSE 框架，并以 3 个场景验证；殷泰晖等[W-6] 实现领域术语增强 Prompt + 规则驱动 SysML 生成 + 多维语义一致性分析，开发原型系统并在真实航天任务中工程验证；吴文瑞[W-7] 给出系统级 SysML 模型分层、依赖、归档与版本控制方案；葛楚妍等[W-5] 的 SmartGen-AADL 用三阶段多智能体把自然语言需求转为 AADL 架构模型，在 15 个场景、4 个主流 LLM 上取得组件错误行占比平均降低 34.37%、结构匹配度提升超 20% 的结果，并做了消融实验。

但必须指出：这类工作主要是**MBSE 的智能体化增强**（智能体扮演需求工程师、架构师），而非系统工程理论本身的更新。**万方核对修正（6.3）**：原稿"几乎没有工作回答如何用 SysML v2 / ISO/IEC/IEEE 42010 架构描述[40] 表达智能体的行为边界、自治等级与治理约束"[R-3][R-4] 的判断需限定——中文研究已给出三条替代建模路径（KARMA[W-4]、AADL[W-5]、SysML 需求建模与一致性分析[W-6][W-7]），说明"用形式化架构模型承载 LLM 生成结果"已不空白；但检索到的中文工作均以**生成需求/架构模型**为目标，未见把自治等级、工具权限与治理约束作为一等建模元素并编译为可执行策略的工作。空白应从"架构描述无人问津"收窄为"**架构描述中的治理语义与可验证性缺位**"，投稿选题 E 相应调整（见 6.8）。反向的关系——用 SE 理论约束智能体系统——在概念上被反复呼吁[5][7][8]，却缺少可操作建模构件。这一空白正是 3.2、5.4 节要展开的投稿切口。

#### 2.2.4 接口与契约

系统工程把接口视为独立管理对象（接口定义、接口控制、变更影响分析）。在智能体系统中，接口有三类：

- **智能体—工具接口**：MCP 以 JSON-RPC 2.0、host/client/server 角色标准化连接[24]；但官方明确协议兼容不等于授权，需 OAuth 资源指示与受众校验、禁止令牌向下游透传、最小权限与增量同意[R-5]。**万方核对（6.4）**：张泉等[W-8] 收集 1 609 个 MCP Server 并细析 200 个，发现平均每个 Server 调用 40.74 个权限接口，52% 的权限验证依赖 API Token 与账号密码、未遵循最小权限原则——把上述"官方建议"升级为有样本量的实测问题。郭帅帅等[W-9] 提出把 MCP 作为"语义控制平面"、用 "Context→QoS/Sec 编译器"把高层任务意图映射为底层 QoS 与安全参数，是"协议解决语法、契约解决语义"论断的具体化方向。
- **智能体—智能体接口**：A2A 处理不透明智能体应用之间的发现、任务生命周期与委派；接收方必须对每次操作按本地策略重新授权，不得继承发起方权限[R-5]。
- **智能体—任务状态接口**：Agent-Integrated Software 提出的 Intent-Level Interaction Abstraction 与"交互契约"，用任务绑定、角色化权限、控制转移与结果证据约束智能体执行与任务状态之间的对应关系，并配套"持续保障"[R-4]。

这三类接口的共同点是：协议解决**语法互操作**，契约解决**语义与责任**。当前 MCP/A2A 快速标准化了语法层，契约层仍以各平台私有实现为主[6][7][R-5]，是理论增量最大的位置。

#### 2.2.5 验证与确认（V&V）

SE 区分"验证（是否按规格建造）"与"确认（是否建造了正确的系统）"。智能体系统使这一区分变得困难：输出是概率性的、轨迹是路径依赖的、规格常以自然语言意图给出。现有做法分三层：

1. **组件级**：单元测试、工具 schema 校验、结构化输出约束；
2. **任务级**：SWE-bench 系列基准（真实 GitHub issue + fail-to-pass/pass-to-pass 测试）[13]、AgentBench 类评测，以及 SWE-agent/OpenHands/Agentless 的可比实验[11][12][14]；
3. **系统级**：轨迹级失效归因（MAST[9]）、LLM-as-a-judge 管道、全链路 trace 与证据捆绑[26]、持续验证与自动回滚[3]。

系统级 V&V 的突出问题是**评估无法区分"模型能力提升"与"编排质量提升"**：同一框架换模型、同一模型换提示版本、不同日期调用同一 API，结果都不可比。已有综述建议冻结模型标识、提示版本、工具 schema 与随机种子，并记录确切评估日期[R-4]；JSS 等期刊亦要求以实证、仿真或形式化证明支撑论断，并鼓励开放科学工件[35]。把"评估配置"本身作为受配置管理的对象，是 SE 可直接贡献的方法论。

#### 2.2.6 配置管理、状态治理与可靠性

图工程提出的**运行时状态图**记录每次状态变更的来源与版本，故障时定位最早失效状态，并选择回放、回滚、分支切换或补偿动作作为恢复边界[6]——这与配置管理中的基线、版本、变更控制几乎逐项对应。工程侧与之配套的模式包括：幂等键与重试安全、编排层去重、断路器与背压、模型回退链与降级模式、按租户/工作流的失效域隔离与爆炸半径控制[R-6]。

可靠性方面有一个被低估的定量事实：若每步可靠性为 0.95，20 步串联的端到端成功率仅约 36%；多智能体系统在生产中报告的失败率区间约为 41%—87%（不同基准与配置差异大，不宜作为单一确定结论）[R-7]。这提示 SE 的可靠性分配、冗余与故障树方法在智能体编排中有直接用武之地，也解释了为何"集中式编排"往往优于自由协商结构[R-7]。

#### 2.2.7 治理、标准与成熟度

把上述治理要求整理为一条可审计链条：AI 资产清单 → 风险分层（数据敏感度 × 自主度 × 爆炸半径）→ 策略即代码 → 运行时执行与审批 → 签名审计与证据 → 持续监控与事件响应 → 管理评审与改进。这条链条同时满足 ISO/IEC 42001 的 PDCA[18]、NIST AI RMF 的四职能[20] 与 EU AI Act 的日志/韧性条款[22]。产业侧已出现借用 CMMI 式五级成熟度的智能体系统工程评估模型（初始级/可重复级/已定义级/可量化级/优化级）[R-4]，但尚未形成可验证的评估工具与跨组织效度证据——这是一个明确的研究空白。

**万方核对新增维度（6.5）**：原稿治理骨架只覆盖 ISO/NIST/EU/OWASP，遗漏中国监管侧。2026 年 5 月 8 日，国家网信办、国家发展改革委、工业和信息化部联合印发《智能体规范应用与创新发展实施意见》[W-24]，部署夯实发展基础（构建标准协议、建立智能体标准体系、完善智能体工具链）、守牢安全底线（明确决策权限、加强行为管控、构建分类分级治理框架）、强化应用牵引（19 个典型场景，其中"研发辅助"明确要求发展软件开发智能体、提升需求分析/架构设计/代码生成/测试全流程能力）与建设创新生态，并要求建立智能体发展评价指标体系。这使"标准缺位"须改为"**国际标准缺位、中国标准体系正在建设**"，同时提升"成熟度模型/分类分级治理"选题的政策相关性。

**表 2　SE 方法 ↔ 智能体工程问题 ↔ 平台机制映射**

|---|---|---|---|

### 2.3 二者结合的最新研究方向

#### 2.3.1 智能体编排：从设计时保证到运行时组织

编排是当前最活跃的交汇点，可沿"确定性—涌现性"轴排列：

- **确定性编排**：LangGraph 式有向图、显式状态 reducer、检查点与人在回路中断[27]；适合合规敏感的交付流程。
- **会话式/协商式编排**：AutoGen 式多智能体对话与群聊管理[R-1]；表达力强但执行顺序不可预测。
- **图工程/系统智能**：显式构造任务组织图、智能体协调图、运行时状态图，把智能体、技能、工具、模型建模为类型化节点，边记录能力归属、资源访问、权限与可靠性；高风险步骤把人类审核者作为显式节点[6]。
- **动态运行时调度**：把任务分解为依赖感知 DAG 并跨并行智能体调度、按语义分发共享上下文，报告约 21%—33% 的执行时间下降与近线性扩展[39][R-8]。
- **软编排（soft orchestration）**：MCP + 推理模型使编排从"显式编码"转向"运行时推断"，架构纪律由设计时保证转移到运行时行为、可观测性与控制[R-4]。这对 V 模型"先设计、后实现"的传统构成实质挑战，也直接催生了"运行时验证"研究需求。

Di Ruscio 等人的分类学研究给出了冷静的评估：智能体、工具、记忆等架构原语已相当成熟，而监控、评估、反馈整合与持续演化能力普遍缺位；治理机制存在灵活性与可控性的固有权衡，需要混合式"灵活编排 + 显式监督"[8]。

#### 2.3.2 CI/CD 自动化：从"交付代码"到"交付智能体"

Harness 的产业实践[1]—[4] 与 Baqar 等人的学术框架[16] 在这一方向形成互补。后者提出：把智能体决策点嵌入 CI/CD 的参考架构、决策分类法与策略即代码护栏模式、**信任分级（trust tiers）** 的渐进自治框架、以 DORA 指标加 AI 特有指标（干预准确率、人工接管率等）的评估方法，以及工业风格案例研究[16]。产业侧对应的具体机制包括自愈 CI（构建失败→根因分析→生成修复分支→重跑流水线）、AI 验证与回滚（自动发现指标、构建健康画像、异常回滚）、Architect Mode（对话式流水线生成并内嵌组织标准）、AI 数据库迁移（向后兼容、策略校验、Git 版本化、回滚脚本、DBA 审批）[3][4]。

更具研究价值的是"智能体自身的交付流水线"：传统 CI/CD 的对象是确定性代码，而智能体的行为由模型版本、提示、工具 schema、记忆内容与策略共同决定。因此门禁必须从"测试通过"扩展为"评估通过"，并把上述配置全部纳入版本控制与可复现性契约。Harness 已在内部实践"按任务基准评测并动态选模 + 护栏回退"[4]。**万方核对修正（6.6）**：原稿"公开文献中尚缺少把这一流程形式化为**准入不变量（admission invariants）** 与运行时验证标准的工作"[R-4] 过于绝对。郭子昌等[W-10] 已在兵棋推演运维场景提出"观测—研判—决策—执行—复盘"Loop，以证据卡片、L0—L3 分级授权、**工具契约**、结构化动作单、可回滚原子动作、配置基线与交付环境漂移闭环约束执行边界；经万方全文接口核验，其正文还要求"已注册工具、权限策略、系统版本与知识条目版本应纳入同一发布管理""未经审核、参数范围失效或回滚路径不可用的工具，应自动从智能体可用清单中下线"。严亚伟、汪东升[W-11] 则给出五元组形式化模型 S=〈T,A,F,M,Π〉与 BayesSchedule 调度算法，在 Pegasus 基准上做 5 组仿真、对比 3 个在线学习基线。二者已构成 L2→L3 的**桥接雏形**；但 [W-10] 作者自述为"原型应用和场景走查"，并明确声明不作普适性能外推、后续才做量化验证，[W-11] 为仿真而非生产平台轨迹。准确表述应是：**已有方法框架与形式化雏形，仍缺在真实交付平台上、经配置冻结的受控实证与可推广的准入不变量标准**。

#### 2.3.3 可观测性：从日志到证据

OpenTelemetry 的 GenAI 语义约定已覆盖 LLM 调用与智能体 span（`invoke_agent`、`execute_tool`），但截至调研时点仍标记为 Development 而非 Stable，需在生产配置中固定语义约定版本[R-5][26]。一条完整的智能体 trace 应串联模型调用 span、检索 span、MCP 工具 span、A2A 任务 span、护栏决策、人工审批与最终工件，目标是"一条连贯的运行轨迹"而非散落日志[R-9]。Harness 的做法更进一步：把每个动作的归因、日志与签名回传为 scorecard 与审计轨迹，供审计方按需调取[2]。**万方核对（6.7）**：《软件学报》根因分析综述[W-12] 把智能体运维归纳为"信息获取—根因定位—效果评估"三流程，并指出该方向仍处早期。需注意中文文献中"可观测智能体"存在术语歧义——高坤[W-21] 的"云网可观测智能体"指**用于观测云网的智能体**，而非**对智能体自身的可观测性**；SLR 检索式须显式排除此类用法，本次万方检索中此类误命中占相当比例。

方法论上必须区分两件事：**trace 上下文只是关联数据，不是授权凭证**；跨信任边界必须重新认证与授权[R-5]。此外，输入/输出内容属性默认应关闭，仅在隐私与留存审批后启用，且不得把密钥或原始提示写入状态文本[R-5]。把"可观测性"直接等同于"合规证据"是常见误用。

#### 2.3.4 治理与保障：从原则到可认证能力

ASOC 把 observability/accountability 列为六项基础原则之一，并把"评估、认证与 Agentic QoS"列为五维研究议程之一[7]；AgentOps 则把智能体纳入云原生治理体系，形成可操作的运营模型[R-6]。综合来看，治理研究正从"列原则"走向三个可检验问题：

1. **自治度如何分级并验证**？按任务/环境/团队分档已在产业实现[2][16]，但缺乏跨组织的分级标准与越界检测。
2. **证据链如何自动生成并抵住审计**？签名动作、策略版本、评估配置三者需时间对齐[R-5]。
3. **Agentic QoS 如何定义与度量**？除延迟/成本外，需纳入干预率、回滚率、失效归因分布等系统级指标[7][9]。

#### 2.3.5 其余值得关注的方向

- **混合符号—神经架构**：ENGINES 项目以 BDI 智能体架构为基座吸收 LLM，用符号侧的确定性、规则执行与可解释性对冲纯 LLM 智能体的可靠性不足[R-10]；呼应安全关键场景对符号方法的偏好。
- **人在回路与组织设计**：把人类审核者作为图的一等节点[6]，以及"人机结合、以人为主"的综合集成研讨厅传统[R-4]，与西方"显式图结构 + 运行时状态治理"路径问题意识重合但语汇不同，二者尚未形成有效对话——中文语境下的低竞争高价值选题。
- **自动化综述与知识生产**：多智能体框架用于文献综述生成已显示出组织与综合质量提升[38]，可作为"智能体承担 SE 知识工作"的元层面案例，但也带来引用准确性风险。
- **平台理论与协议生态**：Agentic AI Platform Networks 识别孤立架构、中介式集成与基于协议的网络化三种集成模式，并以 MCP/A2A 为网络编排基础[R-4]；协议快速标准化而语义层与治理层理论薄弱，是"本体工程"提法的动因[6]。

|---|---|---|---|---|

读表要点有三：

1. **没有全栈赢家**。DevOps 平台型在变更控制、审计与回滚上明显领先，但在编排表达力、状态恢复与基准化评估上落后；开发框架型恰好相反。这正是"融合"研究的产业动机。
2. **SE 覆盖高度偏斜**。除 Harness 与 GitHub 外，多数平台把治理、V&V、配置管理留给了使用方，形成"平台负责能力、组织负责纪律"的隐性契约，而这一契约在学术文献中几乎未被形式化。
3. **研究型 harness 的不可替代性**。SWE-agent 与 OpenHands 虽无企业治理能力，却提供了受控、可复现、可消融的实验台；任何声称"编排改进带来收益"的实证研究，都应在这一类 harness 上做配置冻结的对照实验，而非在商业平台上做前后对比。
4. **中文落地证据补强低代码平台行（6.9）**：罗岚等[W-17] 在浙江省血液中心以 Dify 作智能体编排平台、DeepSeek 作推理引擎、MCP 封装地图/数据库工具、BGE-M3 构建 RAG 知识库，并采用双 LLM 协同校验与 Docker 私有化部署；王湘平[W-18] 给出 "MCP + RAG + 低代码" 的广电故障诊断智能体构建方法。二者印证表 4 中"Dify 类低代码平台"的工具互操作与快速原型定位，也说明中文产业落地已普遍采用"平台 + 协议 + 检索"三件套。苗延飞等[W-19] 把 MCP 用于无人集群作战效能评估（载《系统工程与电子技术》），是协议机制进入系统工程场景的直接例证。

### 3.2 三级融合深度模型

本文提出一个用于定位现有工作的分级：

| 层级 | 含义 | 典型表现 | 代表 |
|---|---|---|---|
| **L1 工具级** | 智能体作为 SE 活动的自动化工具 | 用 LLM 写需求、生成测试、修复构建 | GenAI Workbench / ID 4.0[R-3]、Architect Mode[3] |
| **L2 流程级** | SE 流程作为智能体的约束基础设施 | 智能体动作被纳入流水线、审批、策略、审计、回滚 | Harness[1][2]、AI-Augmented CI/CD[16] |
| **L3 理论级** | SE 理论被改写以刻画智能体特有的涌现、自治与责任 | 系统论、交互契约、图工程、Agentic QoS、成熟度模型 | [5][6][7][R-4] |

关键观察是**产业与学术的错配**：工业平台几乎全部停留在 L2（且做得很扎实），学术倡议几乎全部指向 L3（且多为立场论文、分类学或研究议程）。**万方核对修正（6.6、6.10）**：原稿"连接 L2 与 L3 的可检验桥接方法几乎无人完成"应改为"**已有中文桥接雏形，但缺真实平台上的受控验证**"。[W-10] 的工程化 Loop 与工具契约、[W-11] 的五元组形式化调度、[W-5] 的多智能体架构模型生成、[W-13] 的四智能体协同检测（工业级数据集，漏报/误报率较基线降约 18.2%/19.1%，并发现 1 个 CVE）均已跨越纯倡议阶段；但前两者为原型走查/仿真，后两者为特定任务的实验验证，均未在真实 CI/CD 平台上做配置冻结的多框架对照。这一收窄反而使空白更可操作：差异点不再是"有没有人做"，而是"**能否在可复现的生产级轨迹上验证契约与状态治理的因果贡献**"。Di Ruscio 等人对"监控、评估、反馈整合与持续演化支持不足"的判断[8]，以及 ASOC 对"生态正在 ad hoc 地重造服务计算基础"的批评[7]，本质上都是对这一断层的描述。这一断层构成 1.3 节 RQ4 的核心答案。

### 3.3 生命周期模型适配性对比

| 模型 | 对智能体系统的适用性 | 主要失效点 |
|---|---|---|
| V 模型（需求↔验证逐级对应） | 适合合规关键、规格可形式化的交付环节 | 意图以自然语言给出，规格随上下文漂移，分解—验证对应关系难以建立 |
| 螺旋 / 增量迭代 | 适合评估驱动的提示与工具迭代 | 每次迭代改变模型/提示版本，若不做配置冻结则结果不可比 |
| DevOps 双环 / 持续交付 | **当前最贴合**，尤其与 DORA 指标、渐进式发布、自动回滚结合[3][16] | 环内"人"的决策被智能体替代后，责任链与审计边界模糊 |
| PDCA 管理体系（ISO 42001）[18] | 适合组织级治理与合规 | 粒度偏粗，缺少工程可执行的技术控制 |
| 运行时保证（runtime assurance） | 最有前景：把纪律从设计时迁移到运行时[6][R-4] | 缺乏标准化的准入不变量与恢复语义 |

结论是：不存在单一替代模型，可行路径是"**DevOps 双环作为执行骨架 + PDCA 作为治理外壳 + 运行时保证作为安全内核**"的组合，而这一组合的形式化描述本身即是可发表的方法学贡献。

### 3.4 证据强度与偏倚分析

- **厂商数据不可复现**：如"部署时间缩短 75%""构建失败率下降 67%"等来自客户案例[1]，无对照、无置信区间、无环境描述，只能作为现象线索，不能作为因果结论。
- **预印本占比过高（已部分改善）**：图工程[6]、MAST[9]、系统理论立场论文[5] 均为 arXiv 预印本或立场性工作；ASOC[7] 与 IEEE Software 分类法[8] 已获会议接收/期刊接收。万方补检后，《软件学报》[W-1][W-5][W-12][W-13][W-16]、《计算机学报》[W-14]、《计算机研究与发展》[W-8] 等中文同行评议文献可替换部分二级资料，证据等级整体提升；但中文工作多为方法/原型/单一场景实验，仍缺生产环境大规模对照，不能据此把综述整体证据强度上调。
- **失败率数字口径不一**：41%—86.7% 区间来自多项独立研究与不同基准配置[R-7][9]，二手来源对同一分类法占比的报告亦有差异，综述中应避免转引为确定常数。
- **基准混淆**：SWE-bench 类基准测的是"任务解决率"，不能推断"编排质量"；把模型升级带来的增益归因于框架是常见的内部效度威胁[R-4]。
- **中文文献覆盖：已补检但仍有明确缺口（6.11）**：本次通过万方完成 8 组主题检索，核实 25 条来源，[W-1]—[W-23] 覆盖智能体软件工程、MBSE、协议安全、可靠性与运维；但检索配额在"中文理论源流"与"法规库"两组用尽，**钱学森"从定性到定量的综合集成法"原始文献[31]、综合集成研讨厅研究脉络，以及《智能体规范应用与创新发展实施意见》的万方法规库原文均未取得**（后者已由中央网信办官网核实）。因此 [31]、5.2 选题 F 与 2.3.5 的相关论断仍须保留"待补检"标记。

### 3.5 四组结构性矛盾

1. **设计时保证 vs 运行时涌现**：软编排把架构决策推迟到运行时[6][R-4]，而 ISO 15288 的技术过程以"先定义、再实现、再验证"为默认假设[17]。
2. **灵活性 vs 可控性**：动态协调提升表达力却放大对 LLM 行为的依赖[8]；Harness 用"同一身份、同一策略、同一证据"把智能体收敛到既有变更控制[2]，代价是自主性天花板。
3. **自治分级 vs 责任归属**：自治度可按任务/环境/团队分档[2][16]，但当智能体跨组织边界经 A2A 委派时，责任链如何不因委派而稀释，标准尚缺[R-5]。
4. **协议互操作 vs 语义治理**：MCP/A2A 解决了"连得上"[24][25]，未解决"能力含义一致"与"策略可移植"，这正是本体工程与 Agentic QoS 的动因[6][7]。

## 4 总结与展望

### 4.1 主要结论

1. **瓶颈已完成迁移**。智能体规模化的约束条件从模型能力转向组合、交付、验证与治理；产业数据（60%—70% 时间在外环[1]）与理论判断（功能性能动性是系统层涌现属性[5]）指向同一结论。
2. **"Harness"的三重含义具有共同内核**：为智能能力套上可控制、可观测、可复现的外部结构；接口设计本身即是系统行为的一阶决定因素[11]。
3. **SE 映射不均衡**。生命周期、治理、变更控制映射较成熟；架构描述、接口契约、V&V 与配置/状态治理映射最薄弱（表 2），而这四项恰是当前生产失效的主要来源[9]。
4. **产业在 L2、学术在 L3，中间缺可复现的桥**（3.2 节）。经万方补检，中文文献已出现工具契约、分级授权与形式化调度等桥接雏形[W-10][W-11][W-5]，但均未在真实交付平台上做配置冻结的受控验证；空白因此收窄为"缺生产级受控实证"，而非"无人尝试"（第 6 章）。
5. **证据基础尚不稳固**。厂商案例、预印本与不可比基准占主导，形式化与实证之间尚未闭合。

### 4.2 未来研究趋势（2—3 年）

- **从"智能体工程"走向"系统智能工程"**：图工程三张图[6] 与本体工程、SysML v2、数字线程概念合流，形成领域方法论骨架。
- **形式化工具系统性引入**：交互契约、准入不变量、隔离保证、持续保障，预期出现面向智能体系统的运行时验证标准[R-4]。
- **生命周期治理与成熟度模型成为竞争焦点**：从"框架比拼"转向"流程与认证比拼"[7][R-4]。
- **混合符号—神经架构回归**：BDI + LLM 的可靠性互补[R-10]。
- **协议生态与平台理论耦合**：MCP/A2A 之上的网络编排、Agent OS 与图原生运行时的形态竞争[R-4][R-6]。
- **评估与基准成为瓶颈议题**：冻结模型标识、提示版本、工具 schema、随机种子与评估日期，报告失效归因分布而非仅报告成功率[R-4][9]。

### 4.3 关键挑战

| 类别 | 挑战 |
|---|---|
| 理论 | 缺少可检验的系统理论；现有多元组抽象[5] 未导出可操作设计规则 |
| 方法 | 尚无等价于 ISO/IEC/IEEE 15288 的智能体生命周期流程规范（中国已启动智能体标准体系建设[W-24]）；KARMA[W-4]/AADL[W-5]/SysML[W-6][W-7] 已能承载 LLM 生成的架构模型，但仍无法把自治等级与治理约束作为一等元素表达并编译为可执行策略 |
| 工程 | 状态丢失、工具误用、绕过 CI/CD 治理、结果"看似合理却不可追溯"[R-6] |
| 评测 | 基准不可比、模型与编排增益混淆、缺少系统级失效归因标准 |
| 治理 | 跨边界委派的责任归属、审计证据的时间一致性、协议语义层缺位 |
| 组织 | 平台工程团队与 AI 团队职责重叠；审计、法务与工程的证据需求不一致 |

### 4.4 一个可操作的研究议程

- **第 1 年**：完成 SLR + 分类法；建立配置冻结的多框架实验台（SWE-agent / OpenHands / LangGraph），采集轨迹并复现 MAST 失效分布。
- **第 2 年**：提出"接口契约 → 准入不变量 → 运行时恢复"的形式化框架，在开源 CI/CD 上实现原型，用反事实回放验证回滚与补偿策略。
- **第 3 年**：与 2—3 家工业伙伴做多案例研究，形成成熟度评估工具，输出可复现工件与数据集，并对齐 ISO/IEC 42001 审计需求。

## 5 投稿潜力评估与投稿指南

> 本部分为面向科研决策的附加内容，不属于综述论文正文；若正式投稿，应删除或改写为"研究议程"一节。

### 5.1 总体判断

**结论：具备 SCI 及以上级别投稿潜力，但"纯描述性综述"不具备。**

分层判断如下：

| 稿件形态 | 可达层级 | 判断 |
|---|---|---|
| 描述性综述（本文现状） | 中文核心 / EI / 一般国际期刊 | 可作为课程报告、技术白皮书或开题报告基础，直接投 SCI Q1 大概率 desk reject |
| 规范 SLR + 分类法（taxonomy）+ 证据地图 | SCI Q2 / CCF B，部分 Q1 | 可行，但需 200+ 篇严格筛选、可复现检索协议、编码一致性检验（Cohen's κ）与超越"年份/venue 统计"的实质性发现[35] |
| SLR + 可检验理论框架 + 受控实证 | **SCI Q1 / CCF A（TSE、TOSEM、ICSE、ASE、FSE）** | 具备明确潜力 |
| 理论框架 + 工业多案例 + 工具原型 + 开放工件 | **SCI Q1 / CCF A，或 JSS In Practice / IEEE Software** | 最具竞争力 |

**为什么现在是窗口期**：(1) 理论锚点刚确立（2025—2026 年的系统理论立场论文[5]、图工程[6]、ASOC[7]、IEEE Software 分类法[8] 均属最新成果）；(2) 标准缺位（无面向智能体的 15288 等价规范）；(3) 产业平台已产生可观测的真实数据（Harness 类平台[1][2]），为实证研究提供场域；(4) 期刊主动开设相关专刊（见 5.5）。

**主要风险**：智能体综述在 2024—2026 年高度同质化；主题时效性强，18 个月审稿周期可能导致"发表即过时"；厂商资料不可复现；若只有分类学而无实证或形式化贡献，容易被评审判为 "a well-written but incremental survey"。**万方补检新增风险（6.8）**：中文文献已出现与推荐选题高度近似的先行工作——[W-10] 的工具契约 + 分级授权 + 可回滚原子动作、[W-11] 的形式化调度模型、[W-5] 的多智能体架构生成、[W-8] 的 MCP 权限实证。投稿时须逐项引用并显式划界（先行工作为原型/仿真/单一场景，本文为生产轨迹上的受控实证与可判定不变量），否则易被熟悉中文文献的审稿人指出重复性。

### 5.2 六个可投稿的具体选题

**选题 A｜面向智能体系统的接口契约与运行时状态治理框架**（最推荐）
- RQ：如何把自然语言意图编译为可强制执行的交互契约？契约如何导出准入不变量与恢复语义？
- 方法：类型化契约语言 + 不变量检查器 + 在 OpenHands/LangGraph 上做故障注入（陈旧读、丢失更新、工具误用、级联幻觉），对比回放/回滚/补偿策略的恢复率与代价。
- 贡献：形式化模型、开源工具、失效归因数据集。
- 目标：IEEE TSE / ACM TOSEM / ICSE / ASE。
- 依据：同时被图工程[6]、AIS 交互契约[R-4]、ASOC[7] 三方指向，且与配置管理/接口管理传统直接对应。
- **万方核对后的必要调整（6.8）**：必须把 [W-10] 列为最接近的先行工作并说明差异——该文已有工具契约、L0—L3 分级授权、结构化动作单与回滚约束，但自述为原型场景走查、未做量化验证、且绑定兵棋运维领域；本文应定位为"把契约编译为可判定的准入不变量，并在真实 CI/CD 轨迹上做配置冻结的对照实验"，而非首次提出契约思想。另需引用 [W-8] 作为"最小权限缺失"的量化动机。

**选题 B｜智能体集成平台的系统工程能力成熟度模型**
- RQ：组织级智能体工程能力可分几级？各级的可观测判据是什么？
- 方法：SLR → Delphi（15—25 位专家，2—3 轮）→ 2—3 家企业的多案例评估 → 效度检验；把 CMMI 式五级结构[R-4] 操作化为可评分条目。
- 目标：Journal of Systems and Software（含 In Practice 轨道）、Information and Software Technology、Empirical Software Engineering。
- 注意：必须有跨组织效度证据，否则易被判为"咨询框架"。

**选题 C｜智能体集成平台的系统文献综述与证据地图**（综述路线的最优形态）
- RQ：平台架构原语如何演化？哪些 SE 关切被覆盖/忽略？产业证据与学术证据的一致性如何？
- 方法：PRISMA/SLR 协议，检索 6 个数据库（含 CNKI/万方补检），双人编码 + κ 一致性，纳入/排除标准与检索式公开，工件存 Zenodo；结论须超越描述统计（JSS 明确要求[35]）。
- 目标：ACM Computing Surveys、JSS、IST、IEEE Software（综述/趋势类）。
- 差异化：现有综述多按"框架功能"分类，本文按"SE 过程覆盖度"分类，这是明确的定位差异。

**选题 D｜智能体交付流水线的准入不变量与自动化验证门禁**
- RQ：智能体的哪些配置必须冻结才能构成可比评估？门禁应拒绝哪些变更？
- 方法：定义评估配置清单 → 在真实 CI 中实现评估门禁 → 用反事实回放量化"模型升级 vs 编排改进"的贡献分离。
- 目标：ICSE / FSE / ASE 短文或 TSE 扩展版；IEEE Software 实践类。
- 依据：CI/CD 智能体化已有框架[16] 与产业实现[3][4]，但门禁的形式化尚空白。

**选题 E｜面向智能体系统的 SysML v2 建模与可追溯性**
- RQ：如何表达自治等级、工具权限、人在回路节点与治理约束？如何从模型生成策略配置？
- 目标：Software and Systems Modeling、IEEE Systems Journal、INCOSE 相关会议、MODELS。
- 依据：MBSE 智能体化已有架构范式[R-3]。**万方核对后收窄（6.3）**："用架构模型承载 LLM 生成"已不空白（KARMA[W-4]、AADL[W-5]、SysML 需求建模[W-6][W-7]），故选题应改为"**面向自治等级与治理约束的架构描述扩展及其到策略配置的可验证编译**"，并把 [W-4]—[W-7] 列为必引 related work。

**选题 F｜综合集成研讨厅与系统智能的理论对话**（中文语境，低竞争）
- RQ：钱学森体系下"从定性到定量的综合集成法"与图工程/系统智能在涌现观、人机关系、控制机制上的异同为何？能否互相补足？
- 目标：《中国科学：信息科学》《自动化学报》《系统工程理论与实践》《软件学报》。
- 风险：易写成纯思辨；建议加入形式化对照表与至少一个实证/仿真案例。
- **万方核对结果（6.11）**：本次检索配额用尽前未能完成"综合集成法 / 从定性到定量 / 钱学森"组的检索，[31] 仍未取得可核实著录；万方收录的《在线学习》2026 年专题导语转述了国家智能体政策与首批高等教育智能体，但不足以支撑理论溯源。**该选题的前置条件仍是 CNKI/万方的定向补检**，切勿按"已核实"处理。

### 5.4 论文结构模板（以选题 A 为例）

1. **Introduction**（1.5 页）：一个真实失效场景 → 现有做法为何失效（引用 MAST 数据[9]）→ 研究空白 → 三条贡献 → 论文路线。
2. **Background & Motivating Study**（2 页）：ISO 15288 过程映射[17]、图工程状态图[6]、交互契约[R-4]；用 30—50 条真实轨迹的先导研究量化问题，避免"我认为"。
3. **Formal Framework**（3—4 页）：契约语法、状态转移语义、不变量定义、恢复动作与代价模型；给出可判定性讨论与定理/命题。
4. **Implementation**（1.5 页）：编译为 OPA/Rego 策略与运行时检查器，与 Harness/Argo/GitHub Actions 的集成方式。
5. **Evaluation**（3—4 页）：RQ1 恢复有效性、RQ2 开销、RQ3 与基线对比、RQ4 消融；报告失效归因分布；配置冻结清单。
6. **Threats to Validity**（1 页）：内部、构念、外部、结论效度，尤其模型版本与评估日期。
7. **Related Work**（1.5 页）：与 ASOC[7]、分类法[8]、图工程[6]、MAST[9]、CI/CD 智能体化[16] 逐项区分。
8. **Conclusion & Data Availability**：工件链接、复现实验脚本、伦理与 LLM 使用声明。

### 5.5 评估设计与可复现性清单

- **基线**：单智能体、无契约的多智能体、MAST 中的战术修复（角色规格改进/拓扑调整）、商业平台的默认护栏（若可访问）。
- **指标**：任务成功率、端到端可靠性、恢复率与恢复代价（回滚步数/令牌/时延）、干预率与人工接管率[16]、失效归因分布（能力不足 / 角色错配 / 通信损失 / 并发异常 / 工具误用）[9][R-4]、DORA 四项指标。
- **必须冻结**：模型标识与版本、提示版本、工具 schema 版本、语义约定版本[R-5]、随机种子、温度、最大步数、评估日期、数据集切片[13][R-4]。
- **必须报告**：每任务成本、API 调用次数、置信区间与效应量、失败案例定性分析；不要只报平均值。
- **工件**：检索协议与编码表（SLR 类）、轨迹数据集、容器化环境、分析脚本、Zenodo DOI；JSS 开放科学政策与 TSE/ICSE 工件评审均对此有明确激励[35]。
