2数据集资源 Datasets & Benchmarks

⚠ 三个必须知道的坑

① 仓库 ID 陷阱：MAST 数据集在 HuggingFace 上的正确 ID 是 mcemri/MAD，网络文章常误写为 mcemri/MAST-Data。用错 ID 会直接 404。文件名为 MAD_full_dataset.json（LLM 标注全量）与 MAD_human_labelled_dataset.json（人工标注子集）。
② 标注量的真实情况：MAST 论文宣称 1,642 条轨迹，但其中仅 19 条为人工标注，其余为经人工标注校准的 LLM-as-a-Judge 标注（judge 与人工一致性 κ=0.77）。你若要报告标注质量，必须自行抽样人工校验并报告 κ，不能直接引用论文数字。
③ 数字不一致：AgentRx 的轨迹数在不同材料中有 115 与 170 两个版本——以最新论文（arXiv:2602.02475）为准：170 条、11 个任务设置、62.5 人时标注量、30 条一致性样本的平均两两 κ=0.89。引用时务必注明版本。

4框架与平台 Frameworks & Platforms

⚑ 关键原则：框架是你的「被测对象」，不是你的「实现载体」

强烈建议自建轻量实验脚手架，而不是直接用现成 Agent 框架做研究平台。原因有三： ① 现成框架的埋点深度不够，你拿不到完整的执行轨迹结构（而轨迹正是你的研究对象）； ② 你需要一个干净的对照基线——用现成框架会让"框架自身的失败"污染"架构模式的失败"； ③ 框架迭代极快，一旦绑定，论文复现性会受影响。

6.1 高风险项（必须提前处理）

H1｜LLM API 不可达或成本失控高阻断性

问题：agentdash 默认依赖 OpenAI API（o1-mini 作为 judge）。若网络不可达或无支付方式，整个标注流水线直接停摆。批量标注 300+ 轨迹的 API 费用也是真实支出。

前置准备（本周内完成）：① 注册 2 家以上服务商（主+备），各充值最小额度；② 国内优先选国内服务商（阿里/DeepSeek/智谱等）；③ 本地部署开源模型作为 judge 备选（VLLM_USE_MODELSCOPE=true + Qwen 系列），注意：不同 judge 的标注结果不可直接混用，必须报告用了哪个。

成本预估：按每条轨迹约 3–6K token 输入、判官输出约 1K token 估算，300 条轨迹单轮标注约 100 万 token 量级。API 费用从数十到数百元不等（取决于模型选择）；若跑多架构多预算对照实验，量级会显著上升——这是必须用本地模型做对照实验的原因。

降级方案：若 API 全部不可用，退回"纯人工标注 + 双人独立标注"路径。按 AgentRx 的 20–24 分钟/条估算，300 条约需 100–120 人时——可压缩到 100 条（约 35–40 人时）以保住阶段关口，但这会降低统计效力，需在论文中说明样本量限制。

H2｜中文 judge 校准不达标高关键路径

问题：MAST 的 judge 是在英文编码/数学任务上校准的（与人工一致性 κ=0.77）。中文轨迹（尤其教学管理类半结构化任务）的标注一致性完全未知。若低于 0.7，后续所有基于自动标注的统计结论都不可信。

前置准备：在第 10 周预留 3 天专门做校准实验，不要拖到阶段四。用 MAD 的 19 条人工标注做外部校准 + 你的 50 条自采中文轨迹做内部校准，双重验证。

降级方案：① 换更强的 judge（成本上升但准确率提升）；② 对争议样本启用双 judge 交叉标注（成本翻倍，仅用于抽样审计而非全量）；③ 极限方案：全量人工标注 + 自动化仅作辅助提示（需相应缩减样本量并调整论文定位）。

H3｜数据规模与统计效力不足高

问题：多智能体实验的失败率本身很高（41–87%），若你的任务集太简单（失败率过低）或样本太少（30 条），都得不到有统计意义的分布。对比参照：MAST 用了 1,642 条、AgentRx 用了 170 条（且标注耗时 62.5 人时）。

应对：① 任务难度要有梯度（从 C-Eval 低难度到 GAOKAO-Bench 长文本推理）；② 每个架构 × 每个预算档至少 50 次重复（这是统计效力的下限，不是理想值）；③ 如果预算不足，优先保证"架构对比"的样本量，而不是"失败分类广度"的样本量——因为前者是你的核心论断，后者是工具。

M1｜框架版本漂移导致不可复现中

问题：AutoGen 已并入 Microsoft Agent Framework 1.0，peer-to-peer GroupChat 不再是旗舰模式；LangGraph 也在快速迭代。若论文写作时框架已变，复现你的结论需要不同代码。

应对：① 实验当天记录 pip freeze 全量快照，存入 environment.yml 并随论文发布；② 在论文中明确报告框架名称+版本号+commit hash；③ 自建脚手架在此处再次体现价值——你的核心代码不依赖任何第三方 Agent 框架，因此不受框架迭代影响。

M2｜研究热点漂移使选题过时中

问题：本路线图的信息基础是 2026 年 10 月的检索结果。AI 领域半年即可换代，若半年后才发现"这个问题已被解决"，选题价值会大打折扣。

应对：① 阶段一先做一次"竞争者扫描"——检索你的三个主选题（校验器完备度、决策溯源、中文域基准）在 2026 年 10 月之后是否已有新工作；② 选择题 ①（中文域失败分类）而非 ②（校验器完备度）作为第一个项目，因为"中文域空白"比"指标空白"更稳固；③ 每年 6 月与 12 月各复核一次。

M3｜教学数据的伦理与合规风险中易被忽略

问题：你的数据优势来自教学场景，这涉及学生个人信息与教学过程数据。若采集学生交互轨迹用于研究并公开发布，存在个人信息保护与知情同意的合规风险。

应对：① 轨迹中的学生身份信息全部匿名化/假名化（用学号哈希或直接去除）；② 采集前告知并取得知情同意（课程内可作为教学环节设计的一部分，但要说明用途）；③ 数据卡中明确写出脱敏流程、同意获取方式、伦理审查情况（如学校有要求）；④ 建议在课程设计中就嵌入"数据伦理"教学环节——这本身就是课程亮点，且能自证合规性。

L1｜学术数据库权限不足低（已有成熟替代）

问题：民办高校订阅档位可能无法访问 IEEE Xplore / Scopus / Web of Science，影响文献完整性与影响因子核算。

应对：arXiv（覆盖 90%+ 前沿）、Semantic Scholar（开放全文与引用图）、OpenReview（公开评审意见，是训练评审视角的最佳材料）、Papers with Code、DBLP（作者与引用关系）、Google Scholar。不必等权限到位再开始。

L2｜本地算力不足低（可绕过）

问题：若开发机无独立显卡（仅核显），无法本地运行较大规模开源模型做批量对照实验。

应对：① 阶段一至三完全不需要 GPU（纯数据分析 + API 调用）；② 需要本地模型时用量化小模型（Qwen 系列 7B/14B AWQ/GPTQ）或 GGUF + llama.cpp 路线；③ 批量实验优先用 API + 本地脚本调度，把并发控制交给 API 侧；④ 魔搭社区提供限额免费 GPU 算力（需注册绑定阿里云）；⑤ 学校通常有实验室或高性能计算资源可申请。不要让"没有 GPU"成为放弃对照实验的理由——用 API 跑对照是可行的。
