这套工具帮你做三件事

① 数据合规自动把关——检查数据能不能合法使用，不合格直接拦住，避免用错数据。
② 操作全过程自动记录——每步做了什么、为什么这样做，全部存成文件，事后可回放核查。
③ 论文自动打分排名——按七个维度打分，告诉你哪篇该录用、哪篇不行、为什么。

▶ 三步开始使用 先看看它能做什么

1它能帮我做什么

三句话看懂。不需要任何技术背景。

🛡️

数据合规自动把关

"这份数据我到底能不能用？"

它会自动检查：数据来源是否合法、有没有学生隐私、是否做过脱敏、使用范围是否超出授权。 一共 12 项检查，其中 8 项是"红线级"。

最关键的一点：不合格会直接拦住。被拦住的数据根本无法进入后续流程， 不会"提醒一下然后照用不误"。

✓ 好处：不用担心无意中用错数据，也不会因为隐私问题被质疑。每次检查都有完整记录可查。
📝

操作全过程记录

"这个结果是怎么得出来的？"

把每一次操作的完整过程存成文件：给了什么指令、AI 怎么想的、调用了什么工具、 工具返回了什么、最后得出什么结论。

全部带时间戳，事后可以一步一步回放，像看录像一样。

✓ 好处：结论可追溯、可复核。写论文时"数据可复现"这一条能直接拿出证据。
📊

论文自动打分排名

"这几篇稿子，哪篇该收？"

按七个维度打分（方法是否严谨、有没有创新、数据是否可靠、写作是否清晰等）， 算出总分后自动排名，告诉你哪篇该录用。

如果有论文数据自相矛盾、来源不明等问题，会被"一票否决"直接排除，不管总分多高。

✓ 好处：打分规则全部公开，每篇都能看到"为什么是这个分"，不是黑箱。

5常见疑问

第一次用最常问的几个问题，点一下看答案。

❓需要安装什么软件吗？⌄

不需要你手动装。电脑上已经配好了运行环境。 你只要按上面三步操作即可。如果换到新电脑，才需要额外配置（见进阶模式的"环境与配置"）。

❓会不会很贵？⌄

很便宜。跑一次完整流程约 3 分钱。原因是它只把必要的信息发给 AI， 不做无意义的重复调用。每条命令执行前后都会显示本次花了多少钱。

如果完全不想花钱，所有命令都可以加 --no-llm，用固定规则代替 AI，功能流程一样。

❓我的数据会不会被传出去？⌄

分两部分：
① 你的原始数据和记录文件都留在这台电脑上，不会自动上传到任何地方。
② 只有需要 AI 判断的那一小段文本（比如论文正文节选、检查项说明）会通过网络发给 DeepSeek 做分析。

所以如果有未脱敏的学生个人信息，必须先做合规检查——检查会拦住这类数据。

❓我不懂编程，能用吗？⌄

能。日常使用只需要"复制—粘贴—回车"三个动作，不需要看懂命令内容。 只有当你要换成自己的论文、自己的数据时，才需要打开一个文本文件（用记事本）改几行字。

每个场景卡片里都写明了"结果在哪看"，按路径打开文件即可。

❓论文打分准不准？我能信吗？⌄

可以当作参考意见，但不要当作最终裁决。诚实地说：

  • 打分规则全部公开，每一分都有理由，不是黑箱
  • 但 AI 打分本身有轻微波动，同一篇论文两次打分可能差 1–2 分
  • 分数线（75 分）是按 6 篇样本定的，样本偏少

所以：分数接近分数线的论文，建议人工再看一遍。用它做初筛和排序是可靠的，做最终决定前请人工复核。

❓结果看不懂怎么办？⌄

每个场景都提供了"结果在哪看"的路径。最常用的两个结果文件是：

  • 论文评审报告：results\reviews\review_report.md —— 用记事本打开，直接能读懂
  • 合规检查记录：data\ethics\ 文件夹里的文件 —— 每个案例一份

如果还是看不懂某项，可以到进阶模式的"全部文档"里找对应说明，或者直接问 AI 助手。

❓能重复跑吗？会把之前的结果弄乱吗？⌄

可以随便重复跑，不会弄乱。每次运行都会追加新记录而不是覆盖， 并且工具会自动区分"这次的结果"和"上次的结果"。

如果记录文件积累太多了想清理，可以把旧文件移到同目录下的 archive 文件夹里（不要直接删除）。

四、失败重试与异常处理策略

4.1 三层错误分类（关键设计）

不同错误必须区别对待——无差别重试会浪费时间并浪费配额：

错误类型HTTP是否重试处置
AuthError401/403❌ 不重试立即抛错，提示检查密钥/余额
InsufficientBalanceError402❌ 不重试立即抛错，提示充值地址
RateLimitError429✅ 重试指数退避 + 抖动
TransientError5xx / 网络错误 / 超时✅ 重试指数退避 + 抖动
DeepSeekError其他 4xx❌ 不重试请求本身有问题，重试无意义
2026-10-09 实测修复：初版未分类 402，导致余额不足时仍重试 4 次
（浪费 7 秒 + 剩余配额），且真实原因被掩盖。修复后 0.65 秒立即失败
并给出明确的充值指引。

4.2 重试机制

  • 最大次数：4 次（max_retries）
  • 退避策略：指数退避 1s → 2s → 4s，加随机抖动（避免请求对齐）
  • 抖动：(uuid4().int % 500) / 1000 秒
  • 不重试的情况：鉴权失败、余额不足、请求格式错误

4.3 单点失败的隔离

原则：单篇论文或单条轨迹失败不中断整批处理。

try:
    scores, raw, cost = self._score_one(paper)
    ...
except Exception as e:
    self.rec.error(e, f"review_paper:{paper.paper_id}")
    # 记录错误事件，继续处理下一篇
finally:
    self.rec.finish("review_paper")   # 阶段必须闭合，否则校验 C5 会失败
finally 里的 finish() 是关键：若异常时忘记闭合阶段，
校验项 C5（阶段配对）会报错——这是刻意的设计，让"漏收尾"无法静默通过。

4.4 降级模式

API 不可用时（无密钥 / 余额不足 / 网络故障），所有模块支持 --no-llm：

模块降级行为
伦理审查跳过 LLM 辅助研判，规则引擎判定完全不受影响
论文评审启用启发式评分（按 8 类方法学特征命中数分档）
轨迹采集记录输入与工具调用，模型输出记为不可用

降级模式的定位：保证流程可跑通、排序有区分度，不代表真实评审质量。 正式评审务必使用 LLM 模式。

4.5 三种典型故障的处置

症状原因处置
InsufficientBalanceError余额不足充值：https://platform.deepseek.com/top_up
AuthError密钥无效检查 config/.env 中的密钥
HTTP 402 但 curl /user/balance 正常多进程竞争消耗余额稍等重试

五、如何校验运行结果

5.1 为什么需要校验

"有输出"不等于"输出对"。

本项目的校验器发现过两个真实缺陷：

  1. 分析脚本字段名猜错 → 统计结果静默全零而不报错
  2. 余额不足时重试逻辑掩盖了真实原因

因此校验是流程的必要环节，不是可选装饰。

5.2 八个校验项

$PY src/pipeline/run_pipeline.py --verify
编号检查内容通过条件
C1JSONL 格式合法每行都能解析为 JSON
C2公共字段齐全10 个 COMMON_FIELDS 无缺失
C3时间戳格式统一且单调ISO 8601 可解析且不逆序
C4seq_no 连续无缺号按 trace_id 分组后为 1..n 连续
C5阶段 enter/exit 配对无未闭合阶段、无错配
C6门禁有效性若声明阻断，之后无 llm_call / review_decision
C7错误事件占比可控error 事件 ≤ 15%
C8LLM 调用未因配额中断无 402 导致的失败

C5 与 C6 是最有价值的检查：

  • C5 保证阶段收尾完整（防止异常路径漏收尾）
  • C6 保证门禁真的生效（防止"声称阻断但实际继续处理"）

5.3 校验失败的排查顺序

C1 失败 → 轨迹文件写入被中断，查磁盘空间与权限
C2 失败 → 代码中有手写 dict 未用 TraceEvent，属编码错误
C3 失败 → 多个进程写同一文件导致时序错乱，改用不同 trace_name
C4 失败 → 有事件写入失败（磁盘满或进程被杀），检查日志
C5 失败 → 有 start() 未配对 finish()，检查异常处理路径
C6 失败 → 门禁被绕过，属严重逻辑错误，必须修复
C7 失败 → 大量 error 事件，先查 C8
C8 失败 → 余额不足，充值后重跑

六、常见问题排查（FAQ）

Q1：报 NameError: name 'THRESHOLD_PROFILE' is not defined

原因：常量定义顺序错误（Python 从上往下执行）。 解决：确保 THRESHOLD_PROFILE 定义在 _ACCEPT_BY_PROFILE 之前。

Q2：评审结果显示所有论文分数完全相同

原因：启发式模式（--no-llm）初版对所有维度赋固定分。 已修复（2026-10-09）：改为按 8 类方法学特征命中数分档。 若仍遇到，确认用的是 LLM 模式而非 --no-llm。

Q3：伦理审查把所有案例都判为 REVIEW

原因：初版规则中，只要 will_publish=True 就判 needs_manual， 导致任何公开数据都无法获得 PASS，门禁失去区分度。 已修复：改为按"数据是否涉及自然人"分级——程序日志不适用个人信息规则。

Q4：合规数据被误判 BLOCKED

原因：正则扫描到长数字串（如订单号、学号）就推翻"不含个人信息"的声明。 已修复：现在扫描命中时判 needs_manual（阻断级但需人工裁决）， 而非直接 fail。理由：正则存在误报，直接阻断会使门禁失去可操作性。

Q5：json.dumps 报错 "Object of type X is not JSON serializable"

原因：payload 中放了不可序列化的对象（如 dataclass、datetime）。 解决：写入前用 asdict() 转换，或手动转成基本类型。 TraceEvent.to_dict() 已对所有字段做处理。

Q6：轨迹文件越来越大，如何归档

建议：每次重要运行前把旧轨迹改名归档：

cd data/teaching_traces
mv pipeline_full.jsonl archive_20261009.jsonl

trace_recorder.py 的 --replay 会自动处理备份与恢复。

Q7：能否把 LLM 换成本地模型

可以，只需替换 DeepSeekClient 的实现，保持接口不变：

class LocalClient:
    def chat(self, prompt, system=None, max_tokens=1200,
             temperature=None, json_mode=False, response_format=None):
        # 调用本地 vLLM / Ollama，返回同构的 LLMResponse
        ...

然后替换各模块的 DeepSeekClient() 即可。 这也是本项目把客户端独立成模块的原因。

5.4 排查顺序（校验失败时）

C1 失败 → 轨迹写入被中断，查磁盘空间/权限
C2 失败 → 代码中有手写 dict 未走 TraceEvent（编码错误）
C3 失败 → 多进程写同一文件；改用不同 trace_name
C4 失败 → 有事件写入失败；先确认该 trace_id 是否属本次运行
C5 失败 → 有 start() 未配对 finish()，检查异常处理路径
C6 失败 → 门禁被绕过（严重逻辑错误，必须修）
C7 失败 → 大量 error 事件，先查 C8
C8 失败 → 余额不足，充值后重跑

5.5 关键设计决策（供论文方法章节引用）

决策理由
伦理判定由规则引擎决定，LLM 仅辅助伦理判定必须确定性、可复现、可审计；LLM 输出有随机性
门禁不提供 force_pass 参数一旦审查可绕过即形同虚设
人工覆盖不得绕过学术不端否决项（O2）否决项对应学术规范红线，不应由人工豁免
override 与自动结果并列保存，不改写保证审计可追溯，可看出"谁改了什么、为什么"
Token 预算必须固定并记录多智能体有 4–15 倍 Token 放大，不固定则架构对比无意义
检测器必须可独立测试"0 处失效"与"检测器失灵"外观相同，必须能区分
校验器只认本次 trace_idappend-only 文件会累积历史，否则本次结论被历史失败污染
record() 在消耗序号前校验参数否则类型错误会静默消耗 seq_no 造成缺号，且报错难懂

三、关键技术点

3.1 数据结构陷阱：为什么必须先探查

问题：网络资料与部分文档称 MAST 的标注字段为 annotations， 但实测发现真实字段名是 mast_annotation。

危害：若沿用错误字段名，代码不会报错，而是静默返回全零统计。 本项目首次运行 analyze_mast.py 时输出"含标注：0"——正是这个陷阱的暴露。

防范措施：

  1. 先探查后编码：inspect_mad.py / diagnose_annotations.py 是前置步骤
  2. 失败要显式：n_labeled == 0 应当是硬错误而非"正常结果"
  3. 实测优先于文档：DATA-SCHEMA.md 是实测记录，优先级高于任何二手资料
这是本项目最重要的一条工程纪律：
在 AI 辅助编程的环境下，代码"能运行"不等于"结果正确"。
静默的全零结果比显式的报错危险得多。

3.2 统计口径问题：为什么偏差 7% 不一定是错误

现状：本项目统计得 36.94% / 33.11% / 29.96%，MAST 论文报告 44% / 31% / 24%， 最大偏差 7.06 个百分点。

可能原因：MAST 论文未明确说明其占比的分母口径。三个候选：

分母候选数值若为该口径时的占比
模式检出总数5,14136.94% / 33.11% / 29.96%（本项目采用）
含失败的轨迹数1,23750.9% / 45.7% / 41.3%
全部轨迹数1,64238.6% / 34.6% / 31.3%

学术规范要求：

  • ❌ 不可直接对比口径不同的数字
  • ✅ 若原论文未说明口径，应在自己的论文中显式声明采用的口径，

并说明"与原论文数值存在口径差异"

  • ✅ 这本身可以成为一个方法论论点：基准论文的报告规范有待改进

3.3 标注可靠性：LLM-as-a-Judge 的双重风险

事实：1,642 条轨迹中，1,638 条的标注由 LLM-as-a-Judge 生成， 仅 19 条为人工标注（另有 4 条为空）。

风险 1（MAST 自身）：judge 在英文编码/数学任务上校准（κ=0.77）， 中文场景的可靠性未知。

风险 2（本项目扩展）：若用同一 judge 标注中文数据， 则是在未验证的前提下外推——这是常见但危险的做法。

防范措施：

  1. 双重校准：外部（19 条人工标注）+ 内部（50 条自采双人标注）
  2. 验收阈值 κ ≥ 0.70，不达标触发降级方案
  3. 论文中必须报告：judge 模型名称、κ 值、校准样本量

一个值得注意的现象（来自 MAST 论文的批评性阅读）： 验证类失败在成功运行的样本中也高频出现—— 即"任务完成了，但校验器本身是坏的，绿色仪表盘不是验证有效的证据"。 这一点是突破点②（校验器完备度）的直接依据。

3.4 Token 预算：多智能体实验的头号混淆变量

为什么关键：多智能体相对单次对话有 4–15 倍的 Token 放大 （Anthropic 官方口径）。若不固定预算，"哪个架构更好"的结论毫无意义。

铁律：

  1. 脚手架层面强制记录 token_usage
  2. 对比时按预算分层，而非按总样本
  3. 报告"成本调整后成功率"（等预算下的表现），而非只报准确率

反例：某项工作报告多智能体比单智能体准确率高 10%， 但未说明 Token 消耗是 15 倍——这样的结论在审稿中会被直接质疑。

3.5 可复现性：从第一天开始，不能事后补

必须从第 1 周就做的事（事后补代价极高）：

事项载体

若不能，则可复现性声明不成立。

FAQ-02　pip 安装中断，提示 SystemExit / 安全删除保护

现象：批量 pip install 多个包时中断，报错类似

File "...shim\sitecustomize.py", line 873, in _check_bulk_delete_guard
SystemExit: 1

原因：pip 在升级旧版本时需要删除旧文件，触发了 WorkBuddy 的 safe-delete 批量删除保护（保护 ~/.workbuddy/ 与系统目录）。

影响：已安装成功的包不受影响，但被中断的那个包可能处于残缺状态。

解决：分批安装，一次只装一个包：

python -m pip install -i https://mirrors.aliyun.com/pypi/simple/ --no-cache-dir <包名>

验证：装完后必须实际 import 一次确认可用（不要只看 pip 的成功提示）：

python -c "import <包名>; print('<包名>', <包名>.__version__)"
教训：pip 报告"Successfully installed"不等于包可用。必须 import 验证。
本项目已在 scripts/setup_env.py 中把该验证固化为自检步骤。

现象：

# 或
ModuleNotFoundError: No module named 'scipy.sparse._base'

原因：残缺安装。包目录存在，但二进制扩展目录（.libs）在 FAQ-02 的 中断中被删除或清空。此时 pip 也会报：

dir "C:/Users/shiyu/.workbuddy/binaries/python/envs/default/Lib/site-packages/<包名>/.libs"

三、安装过程中遇到的实际故障

故障 1：pip 批量安装被 WorkBuddy 安全删除保护拦截

现象：一次安装 7 个包时，pip 在升级旧版本过程中需要删除旧文件， 触发 WorkBuddy 的 safe-delete 批量删除保护，导致 SystemExit: 1 中断。

处置：改为分批安装、失败者单独重试。不影响最终环境完整性， 因为 pip 的删除动作发生在版本升级的中途，已完成的包不受影响。

教学意义：这个故障本身是一个可写进论文"可复现性陷阱"小节的真实案例—— 在受管控的研究环境中，包管理器的临时文件操作可能被安全策略拦截。 同类问题在受限科研机构与企业环境中并不罕见。

故障 2（更严重）：scipy / scikit-learn 反复残缺安装，最终无法修复

现象：--force-reinstall 与 --ignore-installed 两种方式均失败：

error: uninstall-no-record-file
Cannot uninstall scikit-learn None
The package's contents are unknown: no RECORD file was found

且重装过程中再次触发 safe-delete 保护（SystemExit: 1）， 导致 scipy/.libs 目录被清空、scipy.sparse._base 缺失：

FileNotFoundError: Could not find module '...site-packages\sklearn\.libs\vcomp140.dll'
ModuleNotFoundError: No module named 'scipy.sparse._base'

排查确认：系统 VC++ 运行库 DLL 均存在（vcomp140.dll 与 vcruntime140.dll 在 System32 与 SysWOW64 下都有），因此不是系统运行库缺失，而是 包自身的二进制目录被安全删除策略清空。

根本原因：pip 的安装流程包含删除被覆盖旧文件这一动作， 而 WorkBuddy 的安全策略会在检测到删除操作时中止进程。 含二进制扩展的大包（scipy 约 40 MB、scikit-learn 约 13 MB）在 安装过程中触发该保护的概率远高于纯 Python 包。
